# GraphRec SRS implementation matrix

Source: `docs/Complete_SRS.pdf`, especially the level 1.1–1.6 activity diagrams (Figures 10–15), use cases UC-01–31, logical data model, and AI engineering pipeline. The pasted implementation brief expands these requirements. Status is based on inspected executable code and tests, not solely on prior project reports. **Implemented** means the principal educational workflow exists; **Partial** names a material missing behavior; **Open** means no usable workflow exists.

## Repository map

| Layer | Current implementation |
| --- | --- |
| Tenant console | React 19, TypeScript, React Router 7 and Vite in `frontend_02/src`; `App.tsx` declares protected routes, `layouts/Layouts.tsx` filters navigation by scope, and `hooks/useResource.ts` manages server reads. |
| Tenant application | `apps/demo-storefront` is a separate FastAPI plus web storefront using the GraphRec SDK. It represents a tenant application; shoppers are not console users. |

| Persistence | SQLAlchemy 2 models in `database/models.py`, PostgreSQL 17, Alembic migrations `0001`–`0034`. Key domain services live under `registration`, `api_keys`, `catalog`, `events`, `datasets`, `models_reg`, `usage`, and `feedback.py`. |
| Async and ML | `graphrec_core/dgsr/worker.py` claims durable training jobs; `dgsr` builds/trains/scores the bounded model. `models_reg/service.py` registers and activates versions, `vector_store` manages Qdrant, and `apps/api/routes/recommendations.py` serves synchronously. Redis (admission control and shared rate limits) is configured in Compose; no Celery, RabbitMQ, RustFS, Kubernetes or pinned inference pod is. Generated artifacts use a persistent local volume. |

## Cross-cutting data and security alignment

The logical entities map to `PricingPlan`, `Tenant`, `TenantUser`, `ApiKey`, `Customer`, `Product`, `CustomerEvent`, `TrainingJob`, `DatasetSnapshot` plus `DatasetSnapshotContent`, `ModelVersion`, `ModelDeployment`, `RecommendationRecord`, `RecommendationResult`, `RecommendationFeedback`, `UsageEvent`, and `AuditLog`. The `Customer` row is a tenant-scoped external shopper identity, distinct from a console user. Migrations `0020`–`0026` add plan editing, operator-assisted recovery, durable sync/batch outcomes, persisted deployment state, normalized ranked results, a tenant-matched result/feedback FK and customer identity FKs. The schema has tenant-local uniqueness for users, credentials, customers, products, events, versions, training/sync/batch request IDs, usage idempotency IDs, recommendation request IDs, ranked result positions/products, and feedback IDs. Database RLS and application predicates both scope owned resources.

The backend uses a consistent `error` envelope with correlation ID. The frontend separates loading, successful empty state, forbidden access and retryable failure. Training does not use browser timers to invent progress; the UI polls persisted job state. The dedicated demo storefront is the customer-facing application and uses real SDK calls.

2. Add fresh cross-version evaluation on one common dataset if model-quality comparison must go beyond each version's training metrics (UC-17).
3. The bounded deployment has Qdrant plus in-process DGSR and tenant-popular fallback. Redis/item-neighbor tiers, a pinned inference pod, RustFS and per-tenant capacity scaling are not present (UC-18/22/26/30).
4. Characterize P95 at supported concurrent load, abrupt worker termination/recovery, and tenant capacity change while preserving another tenant's service. A warm sequential probe does not prove these objectives.
5. Verify exhaustive infrastructure-failure capture and remove any remaining unused UI/code only after confirming it is dead (UC-31).
